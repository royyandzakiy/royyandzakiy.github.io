Blog UI wireframes

Nineteen different feels (the recommended one first) for royyandzakiy.com. Each one is drawn at real size (a 1280×800 desktop and a 390×844 phone) and scaled down, so the proportions are true. They all work with no JavaScript, system fonts and one CSS file.

20. Light terminal (expanded)

The terminal vibe from #1 on a light, paper-white background. Every page is "the output of a command", but the links are real links and nothing pretends to be interactive. The content column is 82 characters wide, like a terminal. Monospace everywhere, system fonts only. The file sizes in the listing are your posts' real sizes.

20a. Home: whoami, ls -l notes/, cat now.txt

The top bar doubles as the prompt and the menu. On phones, the permissions and size columns drop out, leaving date and name.

20b. A post: cat notes/…md

The front matter shows as a grey block, the title as a Markdown heading, code in a light box. Prev/next at the bottom as a command. Still a comfortable 82-column read.

20c. Projects: tree projects/

Your repos as a directory tree with # comments. Each name links to GitHub. On phones the comments drop out so the tree fits.

20d. Talks: column -t talks.csv

A star column, year, event, title. Starred talks first. On phones the event column drops out.

20e. Uses: neofetch

Your toolchain as a neofetch screen: a little ASCII chip on the left, key: value lines on the right. Instantly recognisable, and honest about being software tools. The chip hides on phones.

20f. About: man royyan

The man page from #18, in this light style. SEE ALSO links out to LinkedIn and GitHub for the real CV.

20g. 404: No such file or directory

The error a shell gives you, plus a way back. A static page can't know the URL you typed, so it shows a generic path; one line of JavaScript could fill in the real one.

19. Application notes (recommended)

Plain, fast reading layout (#3), but every post is framed like a vendor application note: a doc number, a revision, an "Applies to" line, and a revision history. The About page gets the full datasheet treatment (#2). Classic technical-doc look, memorable to embedded readers, and the posts stay the point.

19a. Home: the list of notes

Still just a post list. Numbers are year-month plus a count within that month (AN-2604-1 is the first note of April 2026), worked out by ssg from the file name, so nobody numbers posts by hand.

19b. A post

A small document header box, an "Applies to" line (one new front-matter key), an abstract, then the normal post. Revision history at the end; ssg could fill it in from the file's git history.

19c. About: the datasheet

The one page where the joke goes all the way: your profile as a part datasheet. It links out to LinkedIn for the real CV.

19d. Projects: "Reference designs"

Vendors call example projects reference designs. One table, grouped like your GitHub README, each row linking to the repo. It's short on purpose; LinkedIn carries the rest.

19e. Uses: "Recommended operating conditions"

Your toolchain, not a hardware bench, written as the datasheet table of the same name. Parameter, value, and a short note on why. Fill in the real values; these come from your repos.

19f. Talks: "Presentations"

Talks with event, year and a slides link, starred ones first. Leave the year blank where you don't remember it rather than guessing.
